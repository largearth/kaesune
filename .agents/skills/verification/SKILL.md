# Verification

実装済みという自己申告では完了にしない。変更が正しいことを、変更のリスクと利用可能な環境に見合う方法で確かめ、再現可能な Evidence を残す。

## 1. 検証を設計する

変更前または実装中に、変更した境界、壊れやすい振る舞い、利用者に見える結果を特定する。リポジトリの [Development Docs](../../../apps/docs/src/content/development/index.md) を確認し、対象パッケージと変更種別に合うコマンド・シナリオを選ぶ。

- 変更対象のフォーマットチェック、lint、関連テストは必ず実行する。
- 型、ビルド、複数ワークスペースへ影響する変更では、必要な `typecheck` と `build` を実行する。ワークスペース全体にまたがる変更では `pnpm lint`、`pnpm typecheck`、`pnpm build` を実行する。
- テストが未整備で関連テストを実行できない場合は、その事実を記録し、変更リスクに応じた代替検証を行う。
- ユーザー向けの画面または操作フローを変更した場合は、実際のプロダクトを起動し、利用者と同じ経路で主要な成功シナリオを操作してスクリーンショットを取得する。削除・取消などの破壊的操作では、実行後に期待する状態になった画面を必ず取得する。エラー状態または空状態を変更した場合は、それらも確認する。

形式的にコマンドを増やすのではなく、変更内容を反証できる検証を選ぶ。データ境界を変えた場合は API・DB の状態も、通信や画面の問題が疑われる場合は console・network 情報も必要に応じて確認する。

## 2. 実行して証跡を残す

各チェックについて、実行コマンドまたは操作シナリオ、結果、対象範囲を記録する。成功だけでなく、失敗・省略・既知の制約とその理由も正確に残す。

ユーザー向けの UI を確認した場合、Reviewer が状態を判断できるスクリーンショットを取得する。取得したローカルファイルだけでは PR Evidence にならない。`pr-evidence` Skill に従って PR 本文にインラインで添付し、表示されることを確認する。証跡は変更の主張を直接裏付ける最小限にし、機密情報を含めない。

## 3. 判定する

全ての必要な検証が成功した場合のみ、検証済みとして扱う。失敗を無視したり、実行していない手動確認を完了と表現したりしない。

### 本番実機確認の例外

本番環境でしか確認できない実機・OS 固有の UI または表示挙動は、次をすべて満たす場合に限り、未実施の実機確認を例外扱いにできる。

- production 前に同等の条件を再現できない理由が具体的である。
- 対象が低リスクの UI または表示挙動に限定され、セキュリティ、認証、権限、データ整合性、金銭計算、破壊的操作、migration に関係しない。
- 静的解析、test、build、設定・配信内容など、production 前に可能な代替検証がすべて成功している。
- `pr-evidence` Skill に従い、例外を適用した事実、未確認範囲、本番反映後の確認手順を PR に記録する。

単に環境構築が難しい、fixture や認証情報がない、検証に時間がかかるという理由では例外を適用しない。例外条件を満たす場合、Verification verdict は `pass` にできるが、実機確認自体を成功した check に含めず、`exception_applied` として未実施の production check を残す。例外条件を満たさない能力不足は従来どおり `blocked-road-maintenance` Skill に従う。

上記の本番実機確認の例外を除き、必要な環境、認証情報、テストデータ、ブラウザ操作、または再現手順が存在せず、正しさを確認できない場合は `blocked-road-maintenance` Skill に従う。

## Deliverable

PR の Verification には、実行したコマンドまたはシナリオと結果を記載する。Evidence にはスクリーンショット、実行結果、console / network、API / DB 状態など、実際に取得できた根拠を記載する。証跡がない検証は、実施済みと書かない。本番実機確認の例外を適用した場合は、実施済みの検証と未実施の production check を分けて記載する。
